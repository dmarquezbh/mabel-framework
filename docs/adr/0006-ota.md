# ADR 0006 — Modelo de atualização em runtime / OTA

- **Status:** Proposto (design de plataforma)
- **Data:** 2026-07-19
- **Contexto do repo:** `github.com/dmarquezbh/mabel-framework`, branch `feat/mabel-arch-consolidation`
- **Irmão de:** ADR 0005 (super-app), 0007 (autoria poliglota). Design em `docs/ota.md`.

## Contexto

No super-app (ADR 0005), o shell nativo é estável e os mini-apps (wasm + descritor) são
conteúdo. Isso abre entrega OTA — features sem reinstalar, e (conforme o nível) sem
loja. Mas há uma tensão real: o caminho **AOT** (rápido) fica *baked* no binário e **não**
é atualizável; só o **interpretador** carrega módulo em runtime e habilita OTA de lógica.
E há restrição de policy na App Store pública (2.5.2) sobre baixar código executável.

Ancoragem factual (spike WASM-on-device, task #17, concluído):
- **WasmKit (interpretador puro-Swift, sem JIT) roda no iPhone via xtool sem Mac** —
  **provado**. Carrega módulos em runtime → habilita OTA nível 2.
- **.NET→wasm não roda no WasmKit** (preview2/Mono vs core-module/preview1) → mini-app
  live-on-iOS = lean core-wasm (Rust/TinyGo/AS/C); .NET fica em autoria/build/desktop.
- **wasm2c-AOT** (velocidade nativa no iOS) também é **PROVADO** no device sem Mac (spike v2,
  ~163× vs interpretador). Os dois runtimes rodam **lado a lado no mesmo app**.

## Decisão

Modelo OTA em **três níveis**, com estratégia combinada:

1. **Nível 1 — descritor-only** (UI/conteúdo, dado puro): OTA **sempre**, em qualquer
   distribuição inclusive loja pública (é dado, não código executável). Loop mais rápido
   e seguro; cobre o grosso das mudanças de UI.
2. **Nível 2 — mini-app WASM (lógica)** via **interpretador**: OTA **livre em
   distribuição interna/MDM**; na **loja pública é zona cinza** (2.5.2; WASM não tem o
   carve-out que o JS tem) → não depender dele em público.
3. **Nível 3 — shell nativo**: só pela loja (raro; shell é fino/estável).

**Estratégia:** core/estável **AOT-baked** (rápido, loja) + mini-apps novos/updates via
**interpretador OTA** (interno) + **descritor-OTA sempre**.

**Policy (honesto):** interno/enterprise/MDM = OTA livre (não passa por App Review).
Loja pública = saídas seguras são descritor-OTA + mini-app webview (carve-out do JS) +
mini-apps AOT-baked; OTA de lógica-WASM público fica cinza.

**Segurança:** descritor não é código (host só instancia controles nativos); mini-app
WASM é código → exige **assinatura/verificação no registry** antes de carregar
(pré-requisito do OTA dinâmico; sandbox+manifesto limitam mas não substituem verificação
de origem).

## Alternativas consideradas

- **Só loja (sem OTA):** perde o trunfo do super-app (features sem reinstalar). Rejeitada.
- **Só interpretador (tudo OTA, nada AOT):** máxima atualizabilidade, mas abre mão da
  velocidade nativa do AOT no caminho crítico. Rejeitada em favor do combinado.
- **Só AOT (tudo baked):** rápido e 100% compatível com loja, mas zero OTA de lógica —
  volta ao ciclo de loja pra cada feature. Rejeitada em favor do combinado.
- **Depender de OTA-WASM na loja pública:** arriscado (2.5.2 é cinza pra WASM).
  Rejeitada — em público usar descritor-OTA/webview/AOT.

## Consequências

- (+) Features e correções sem reinstalar (interno); mudança de UI instantânea em
  qualquer canal (descritor-OTA).
- (+) Combina velocidade (AOT no core) e agilidade (interpretador nos mini-apps).
- (−) Dois caminhos de runtime a manter (AOT + interpretador) e a disciplina de escolher
  por mini-app.
- (−) OTA de lógica na loja pública fica fora (cinza) — features públicas dependem de
  descritor-OTA/webview/AOT ou de release pela loja.
- (−) OTA dinâmico exige registry com assinatura/verificação (ainda não desenhado).
